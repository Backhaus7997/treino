# Bugs encontrados corriendo el E2E trainer→athlete (2026-08-07)

Contexto: se corrió el flow completo (PF se registra → ofrece servicios → alumno lo busca en mapa/lista → chatean → se vinculan → PF crea y asigna rutina → alumno la ejecuta y carga datos/fotos) contra el Firebase Emulator Suite local (`treino-dev`, JDK 21, seed `scripts/seed_emulator_full.js` + catálogo real de 793 ejercicios vía `scripts/import_enriched_catalog.js --write --replace`). Simuladores iOS con ubicación forzada a Buenos Aires (-34.5786,-58.4243) para coincidir con los PFs sembrados.

Cada entrada: severidad, repro, evidencia (archivo:línea cuando aplica), y si bloquea el demo o sólo degrada.

---

## Abiertos

### [CONFIRMADO] La sesión de Auth vieja (prod) queda pegada al cambiar a USE_EMULATOR y deja al usuario atrapado

- **Severidad**: alta (rompe el arranque limpio, no el producto en sí)
- **Repro**: con la app instalada previamente contra `treino-dev` real, reinstalar el mismo bundle compilado con `--dart-define=USE_EMULATOR=true` y lanzar. La sesión de Firebase Auth persiste en el Keychain del simulador (independiente de qué backend apunte Firestore), así que la app arranca "logueada" contra un uid que no existe en el Firestore-emulador → pantalla "No pudimos cargar este perfil". Tocar "Cerrar sesión" no vuelve a Welcome/Login: cae directo en `ProfileSetup` paso 1 con un username `@julieta` pre-cargado (draft viejo, no del seed), y el botón X de arriba a la izquierda no navega a ningún lado (probable `PopScope(canPop:false)` o gate similar atrapando la ruta).
- **Evidencia**: capturas de pantalla en vivo, iPhone 16 Pro (848979B2-B924-4AC5-9F8C-19563AFA6A04), 2026-08-07 ~10:11.
- **Corrección tras repro**: `xcrun simctl uninstall` + reinstalar el `.app` NO alcanza — el Keychain del simulador sobrevive al desinstalar (comportamiento estándar de iOS, no bug de TREINO), así que la sesión vieja siguió pegada incluso con el bundle recién instalado. El fix real que funcionó fue `xcrun simctl erase` (borra TODO el contenido del dispositivo) + reboot.
- **Workaround usado**: `xcrun simctl erase <udid>` antes de instalar.
- **Bloquea el demo**: no, con el workaround. Pero sí es una trampa real de producto: si un usuario real cambia de cuenta o el equipo reutiliza un dispositivo de test, la app queda en un estado sin salida in-app (la X de ProfileSetup no navega, no hay forma de volver a Welcome/Login desde ahí). Vale la pena que alguien del equipo lo repita en un dispositivo real fuera de este contexto de emulador para confirmar si aplica también ahí.

### [A VERIFICAR EN VIVO] `trainerPublicProfiles.displayNameLowercase` no se escribe al completar onboarding desde la UI

- **Severidad**: crítica (verificado por auditoría de código, pendiente de reproducir en este run)
- **Detalle**: `orderBy('displayNameLowercase')` en el fallback sin-ubicación de discovery (`lib/features/coach/data/trainer_public_profile_repository.dart:77`) descarta silenciosamente cualquier doc sin ese campo. El único writer (`user_repository.dart:194-198`) lo setea sólo si `displayName` llega en el mismo partial que un campo trainer — cosa que `profile_edit_trainer_screen.dart` nunca hace. El seed sí lo escribe a mano, por eso nunca se detectó en demos previas.
- **Impacto si se confirma**: un alumno que niega ubicación ve lista vacía aunque haya PFs reales cargados. Sin error visible.
- **Estado**: pendiente — se va a confirmar con el PF creado a mano en este mismo run.

### [DESCARTADO — error de tooling, no del producto] `EMPEZAR` parecía deshabilitado para siempre

- **Síntoma observado**: ningún tap sobre EMPEZAR, GOOGLE, APPLE, "Iniciar sesión" ni siquiera el botón HOME físico tenían efecto visible, incluso tras `simctl erase` completo, rebuild limpio y reboot del simulador.
- **Descarte de hipótesis intermedias** (documentadas por transparencia, ambas resultaron falsas): (1) que `USE_EMULATOR` no quedara embebido en el build — un `print` de diagnóstico confirmó `useEmulator=true` y que `AuthNotifier.build()` resolvía a `null` en ~340ms, nada colgado; (2) que el LaunchScreen nativo tapara la vista de Flutter — el storyboard es el genérico de Flutter, visualmente nada que ver con el Welcome real.
- **Causa raíz real**: mis coordenadas de tap estaban mal calculadas. La herramienta de control del simulador reporta el espacio de coordenadas en **puntos del dispositivo** (ej. 402×874 para iPhone 16 Pro, 430×932 para iPhone 15 Pro Max), no en píxeles del screenshot. Usé valores leídos a ojo del screenshot (ej. `y=1451`) que **excedían el máximo del eje** (874/932), cayendo fuera de la pantalla. Confirmado con un `print` dentro del propio `onPressed` de EMPEZAR: no se disparaba con ninguna de mis coordenadas iniciales, y sí se disparó al barrer sistemáticamente valores de `y` dentro del rango válido.
- **Nada que reportar en el producto** — cero cambios de código quedaron en el repo (los 3 `print` de diagnóstico se revirtieron con `git checkout`).
- **Aprendizaje para futuras sesiones**: con este simulator-control tool, siempre convertir a puntos del dispositivo (el valor que devuelve `attach`), nunca usar coordenadas leídas de un screenshot como si fueran 1:1.

### [LIMITACIÓN DE ENTORNO — no es un bug de TREINO] El canal de input del simulador es intermitente en esta sesión

- Después de resolver el problema de calibración de coordenadas (ver arriba), el tap sobre EMPEZAR funcionó una vez. Pero en la pantalla de registro, taps repetidos sobre el campo EMAIL y sobre CREAR CUENTA (con las mismas coordenadas correctas, verificadas contra el mismo espacio de puntos) no produjeron ningún efecto visible (sin foco, sin teclado, sin snackbar de validación).
- Adicionalmente, el texto inyectado vía `text` tradujo el carácter `@` en una comilla tipográfica `"` (`coach.demo@emulator.treino` → `coach.demo"emulator.treino`), probablemente por un mapeo de teclado incorrecto entre la herramienta de input y el layout activo del simulador (es-AR vs en-US).
- Esto es una limitación del canal de automatización (`mcp__Claude_Code_iOS_Simulator__control`) en este entorno puntual, no del código de TREINO — la sesión ya demostró que la UI responde correctamente cuando el input se entrega (navegación Welcome → Registro funcionó).
- **Actualización tras seguir insistiendo**: encontré y arreglé una causa real — `defaults read com.apple.iphonesimulator ConnectHardwareKeyboard` daba `1`, es decir el simulador tenía activo el passthrough de teclado físico, por eso el teclado en pantalla nunca aparecía. Lo desactivé (`defaults write com.apple.iphonesimulator ConnectHardwareKeyboard -bool false`) y reboteé. Mejoró la tasa de éxito de los taps (usando `touch_path` con hold de ~100-150ms en vez de `tap` simple) pero **no la volvió consistente**: navegación Welcome→Registro funcionó de forma repetible, pero el foco + tipeo en el campo EMAIL del form de registro siguió fallando en la mayoría de los intentos, sin patrón claro (mismas coordenadas, a veces sí a veces no).
- **Sin poder completar el registro real vía UI en esta sesión**, el resto del flow E2E (alumno busca al PF, chat, vínculo, asignación de rutina, ejecución) queda pendiente de una corrida con input más confiable (dispositivo real, o Xcode conectado directamente, o Appium/WebDriverAgent en vez de esta herramienta de control).

## Notas de entorno (no son bugs de producto)

- `scripts/emulator.sh:16-21` es incorrecto: dice que `SKIP_FUNCTIONS=1` evita el requisito de Java 21+, pero Firestore y Auth también son procesos Java — el gate corre antes de bootear cualquier emulador, con o sin functions.
- JDK 21 ya estaba instalado vía `brew install openjdk@21` pero no registrado en `/usr/libexec/java_home` — sólo hizo falta exportar `JAVA_HOME` apuntando al prefix de Homebrew, cero instalación nueva.
- `flutter run -d <device> --dart-define=USE_EMULATOR=true` corrido en background (sin TTY) muere silenciosamente después de "Xcode build done" sin instalar el binario ni loguear error — hay que buildear y usar `xcrun simctl install/launch` a mano.
